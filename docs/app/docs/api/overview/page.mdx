# API Reference: Overview

`stellar-stream-hive-api` is a Rust/Axum service that reads Soroban RPC, decodes
Soroban events emitted by the [Stream contract](/docs/contracts/stream), and
serves the resulting index over a small REST API. It holds everything
in memory (no database). On boot its first poll reaches back
`INDEXER_BACKFILL_LEDGERS` ledgers (default 17,280, about a day), then it
resumes from the last event cursor -- see the
[API repository's README](https://github.com/Stellar-Hive/stellar-stream-hive-api/blob/main/api/README.md)
for why.

Source: [`stellar-stream-hive-api`](https://github.com/Stellar-Hive/stellar-stream-hive-api)
(`api/` directory).

## Base URL

There is no hosted, publicly-maintained instance yet. Run it yourself:

```bash
git clone https://github.com/Stellar-Hive/stellar-stream-hive-api.git
cd stellar-stream-hive-api/api
cargo run
```

By default it binds to `http://localhost:8080`. Every example on these API
reference pages uses `http://localhost:8080` as the base URL -- substitute
your own deployment's host.

## Endpoints

| Method | Path | Description |
|---|---|---|
| `GET` | [`/streams`](/docs/api/streams#get-streams) | All known streams, with live-computed accrual |
| `GET` | [`/streams/:id`](/docs/api/streams#get-streamsid) | One stream's full detail |
| `GET` | [`/senders/:address`](/docs/api/streams#get-sendersaddress) | Streams sent by an address |
| `GET` | [`/recipients/:address`](/docs/api/streams#get-recipientsaddress) | Streams received by an address |
| `GET` | [`/stats`](/docs/api/stats) | Aggregate totals across every indexed stream |
| `GET` | `/health` | Liveness check; always returns `200 ok` |
| `GET` | `/ready` | Readiness: `{ synced, latest_ledger, contract_configured, indexed_streams }` |

## Response conventions

- Every response is `application/json`.
- **Amounts are decimal strings, not JSON numbers.** `total_amount`,
  `withdrawn`, `streamed_amount`, `withdrawable_amount`, `total_streamed`, and
  `total_withdrawn` are all serialized as strings (e.g. `"30000000000"`), not
  numbers. This is deliberate: these are `i128` values on-chain, and JSON
  numbers are IEEE-754 doubles in JavaScript/TypeScript, which only represent
  integers exactly up to 2<sup>53</sup> -- well below what a large stream's
  stroop amount can reach. Parse them with `BigInt("30000000000")` in
  JS/TS, or the equivalent big-integer type in your language. See
  [Integration Guide](/docs/integration#computing-streamed_amount-client-side)
  for a worked example.
- Addresses (`sender`, `recipient`, `token`) are Stellar strkeys (`G...` for
  accounts, `C...` for contracts), exactly as they appear on-chain -- no
  reformatting.
- `streamed_amount`, `withdrawable_amount`, and `progress_percent` on every
  stream view are computed **live**, against the indexer's most recently
  observed ledger, on every request -- they are never stale beyond
  the indexer's poll interval (10 seconds by default).

## Error format

Non-2xx responses return:

```json
{
  "error": "not_found",
  "message": "stream '42' not found"
}
```

| HTTP status | `error` | When |
|---|---|---|
| `400` | `bad_request` | A path parameter failed basic validation (e.g. an empty address). |
| `404` | `not_found` | The requested stream id doesn't exist in the index. |
| `502` | `upstream_unavailable` | Reserved for future endpoints that proxy live Horizon reads; unused by the current routes, which only ever read already-indexed in-memory state. |
| `500` | `internal_error` | An unexpected server-side failure (e.g. arithmetic overflow computing aggregate stats). Logged server-side with full detail; the response body never leaks internals. |

### Why `/streams/:id` can 404 even for a real stream id

<CalloutBox variant="info">
  The indexer only knows about streams whose `create` event it has
  actually observed within its backfill window -- the first
  `INDEXER_BACKFILL_LEDGERS` ledgers (default 17,280, about a day) on
  boot, then every ledger it polls from the last event cursor onward (see
  [why no database](https://github.com/Stellar-Hive/stellar-stream-hive-api/blob/main/api/README.md#why-no-database)).
  If you query a stream id that was created before that backfill window,
  or before `STREAM_CONTRACT_ID` was configured, expect a `404` until the
  relevant event has been re-observed. This is a known v1 limitation, not
  a bug.
</CalloutBox>

## Health and readiness

Two unauthenticated endpoints exist for monitoring and orchestration.

### `GET /health`

```bash
curl http://localhost:8080/health
```

Returns the plain text `ok` with status `200`. It only signals that the HTTP
server is up and answering -- it says nothing about whether the indexer has
synced.

### `GET /ready`

```bash
curl http://localhost:8080/ready
```

```json
{
  "synced": true,
  "latest_ledger": 123456,
  "contract_configured": true,
  "indexed_streams": 42
}
```

`/ready` **always responds `200`**, even when the indexer is not ready, so
clients must read the body rather than relying on the status code:

- `synced` is `false` until the indexer has observed a ledger from Soroban RPC.
  While it is `false`, `latest_ledger` is `0` and no events have been processed
  yet.
- `contract_configured` is `false` when `STREAM_CONTRACT_ID` is unset or is not
  a real `C...` contract address. In that case no stream events can be decoded
  and `/streams` stays empty.
- `latest_ledger` is the most recently observed ledger sequence number.
- `indexed_streams` is the number of streams currently held in memory.

## Response headers

| Header | When | Meaning |
|---|---|---|
| `Content-Type` | Every response | `application/json` |
| `X-Total-Count` | List endpoints: `/streams`, `/senders/:address`, `/recipients/:address` | The number of matching items **before** `limit`/`offset` are applied |

`X-Total-Count` is exposed to browsers via `Access-Control-Expose-Headers`, so
cross-origin scripts can read it and page through list results. See
[Filtering and pagination](/docs/api/streams#filtering-and-pagination) on the
Streams page for how `limit` and `offset` interact with it.

## CORS

`Access-Control-Allow-Origin` defaults to `*` (any origin). Setting
`CORS_ALLOWED_ORIGINS` to a comma-separated list of origins restricts it to
only those origins; leaving it unset, or setting it to a lone `*`, means any
origin. Whitespace and trailing slashes are trimmed from each entry.

Allowed methods are `GET`, `HEAD`, and `OPTIONS`. Only the `Accept` and
`Content-Type` request headers are allowed. `X-Total-Count` is exposed to
browsers via `Access-Control-Expose-Headers` so cross-origin scripts can page
through list results.

The policy is permissive by default because every endpoint is read-only public
data with no notion of a logged-in user -- there is nothing a cross-origin
request could do here that a same-origin one couldn't.

## Environment variables

| Name | Default | Meaning |
|---|---|---|
| `SOROBAN_RPC_URL` | `https://soroban-testnet.stellar.org` | Soroban RPC endpoint the indexer polls for events. |
| `STREAM_CONTRACT_ID` | _(unset)_ | The Stream contract id to index. Unset means the indexer runs but `/streams` stays empty. |
| `BIND_ADDR` | `0.0.0.0:8080` | Address and port the HTTP server binds to. |
| `POLL_INTERVAL_SECS` | `10` | Seconds between Soroban RPC polls. |
| `INDEXER_BACKFILL_LEDGERS` | `17280` | How many ledgers back the indexer starts from on boot. |
| `CORS_ALLOWED_ORIGINS` | _(unset -- any origin)_ | Comma-separated list of allowed origins; unset or `*` means any origin. |
| `RUST_LOG` | `info` | Log filter for the service (e.g. `debug`, `info`, `warn`). |
